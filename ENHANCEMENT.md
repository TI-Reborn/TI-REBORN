# Улучшение предметов — 2026-09-19

Реализован обычный Upgrade Kit (шаблон 30) через исходную команду клиента
`C8 2A`: один набор на одну попытку. Максимум **+25**. Переходы 0→1 и 1→2
имеют шанс 100%, последующие — 63%. Неудача уничтожает обычный предмет;
SE остаётся с +0 и начальной прочностью. SE определяется по исходному
`special=1` или сохранённому флагу экземпляра, а не по тексту имени.

## Основания правил

- [Руководство Total Influence, © 2008–2011 Light Vision Interactive](https://ti.ggeek.ru/files/TIO_manual.pdf),
  печатная стр. 83: одноразовый набор, безопасные +1/+2, шанс 63%, +65 к
  максимальной прочности при успехе, уничтожение обычного предмета и сброс SE.
  Это опубликованные исторические правила. Значения последнего официального
  сервера данной сборки не сохранились в имеющихся исходных данных.
- В установленном `silver.dll` шанс НЕ зашит константой. Окно `7C3904`
  читает серверные настройки `[AC5AC0]+5` (безопасный уровень), `+6` (броня),
  `+7` (оружие). Ветка `7C4218..7C42D6` подменяет шанс на 100% ниже
  безопасного уровня. Конфигурация эмулятора использует значения руководства.
- XML-загрузчик `A712FD` задаёт стандартный предел 25 (`metadata+649`),
  `A7BE80` возвращает этот предел. Общий `CanEnhance A7A9BC` допускает уровни
  ниже 27 для расширенных вариантов механики; специальные наборы и +26/+27
  в этой реализации не поддерживаются. Сервер проверяет предел независимо от UI.
- Наборы LE, конвертация в SE, Damage Upgrade Kit и улучшение за отдельные
  очки требуют других правил. Запрос без обычного набора отклоняется.

## Сеть, сохранение, параметры

- Builder `99F25C`, writer `6419A8`: `C8 2A u32 target u8 hasKit [u32 kit]`.
  Идентификаторы — экземпляры, не шаблоны. Сервер находит их только среди
  наёмников текущего аккаунта; набор и предмет могут находиться у разных своих
  наёмников. Улучшение в комнате/бою запрещено.
- Расход набора, изменение/удаление предмета и резервирование израсходованных
  ID выполняются в одной SQLite `BEGIN IMMEDIATE` транзакции. Ответ содержит
  полные ItemList30 изменённых владельцев, затем F0/151 (успех), /152
  (уничтожение) либо /157 (SE неудача). 151/152 принимают шаблон и уровень;
  потребитель `7D2352` преобразует шаблон в локализованное имя.
- ItemList содержит два уровня: `unknown_bytes_02[0]` — отображаемый/действующий
  уровень, getter `63C958` → TItem+4E; `unknown_bytes_03[0]` — сохранённый.
  Оба обновляются. Склад уже сохраняет исходную запись и уровень экземпляра.
- При успехе максимум прочности увеличивается на 65. **Локальная политика**
  этой реализации полностью восстанавливает текущую прочность и выставляет
  расчётный максимум равным новому максимуму. Руководство не уточняет судьбу
  текущего износа; серверной формулы для изношенных вещей нет.
- `config/enhancement.json` содержит предел, шанс, безопасные уровни и
  прибавку прочности. После изменения настроек нужен перезапуск эмулятора/клиента.
- Полный пакет серверных настроек ещё не восстановлен. Лаунчер временно
  выставляет три поля настроек в памяти оригинального клиента перед показом
  окна и расчётом характеристик, как уже делает для тарифа лечения. Файл DLL
  на диске не изменяется. Отдельный немодифицированный запуск без лаунчера
  эту синхронизацию пока не получает.

## Характеристики

Текущая сборка отличается от примерной формулы старого руководства. При
безопасном уровне 2: бонус оружия `min(L,2)+2*max(L-2,0)`; бонус брони
`min(L,2)+floor(1.5*max(L-2,0))`.

`A7A525..A7A576` прибавляет бонус к обоим концам диапазона урона **до**
масштабирования навыком в `A7A826..A7A890`. `A7ADE4` вычисляет броню с
усечением дробного бонуса. Эмулятор использует порядок текущего клиента.
Изменение применяется в серверном бою, а не только в подписи предмета.
Прежние ограничения боевого движка (особые эффекты RPG/огнемёта и др.,
неподдерживаемая экипировка части комплексной брони) этим изменением не снимаются.
Ограничения эффективности заточки по уровням/типам комнат отдельно не реализованы.

Проверены границы 62/63, безопасные попытки, SE-шаблоны, предел, повторное

Эти проверки не заменяют ручную проверку окна улучшения в живой игре.

## Тест в игре

1. Закрыть текущую игру и заново запустить
   `python tools/run_reservation.py` из папки эмулятора (или привычный ярлык лаунчера).
2. В городе использовать Upgrade Kit на недорогом оружии/броне. Окно должно
   показывать 100% для +1 и +2, затем 63%. За попытку исчезает один набор.
3. После улучшения проверить подпись, характеристики и сохранение при перезапуске.
4. На SE проверить, что неудача оставляет предмет, снимая всю заточку до +0.
   На обычном предмете неудача должна удалить именно выбранный экземпляр.

Сервер пишет `enhancement_committed`/`enhancement_rejected` в отчёт сессии.
Основная база игрока автоматическими попытками не изменялась.

## Исправление видимости наборов — 2026-09-19

По скриншотам пользователя Upgrade Kit был виден в примерочной магазина,
но отсутствовал в инвентаре бойца слева на странице склада. Наборы оставались
в SQLite (в том числе экземпляры 1062/1063 у бойца3); потери покупки не было.

Исходный клиент включает `HideUpgradeBoxes` (+2A2) у панели инвентаря страницы
отряда: `9A7F3A`, глобальный указатель `AC4BD4`. Проверка `IsSimpleUpgradeKit`
`A7B8D0` сравнивает именно шаблон30. Флаг используется для отрисовки, раскладки,
попадания мышью и обработки действий — шесть веток `9BC62A`, `9BCAFD`,
`9BCE56`, `9BE89D`, `9BEE12`, `9BF063`. Магазин не включает этот флаг.

`tools/upgrade_kit_inventory.js` выключает скрытие у панели склада и при
создании обычного окна инвентаря. Уже созданная до установки перехватов панель
склада обрабатывается сразу через `AC4BD4`. Панели обмена и сам предикат типа
предмета не изменяются. Код подключён к стандартному лаунчеру. Это временная
совместимость интерфейса с физическими наборами из старого каталога; DLL на
диске и купленные предметы не переписываются.

Исходная ветка применения `A65A10..A65A7E` для типа13 сохраняет ID набора
в `AC4DB0`, шаблон в `AC4DB4` и включает выбор предмета (режим1). Живая проверка
подтвердила тип13, `usable=1`, а также что `AC567C` действительно указывает на
`AC4DB0`, откуда окно улучшения берёт набор для команды C8/2A.

Проверка `tools/verify_upgrade_kit_inventory_native.py`: 36 оригинальных
веток видимости/обработки мыши, два места установки свойства, переход в выбор
цели — PASS. Живая проверка `evidence/upgrade_kit_inventory_live.json`:
свойство панели изменено 1→0. Автоматического применения наборов к вещам
основного аккаунта не выполнялось; нажатия и результат в игре проверяет пользователь.

Пользователь подтвердил в живой игре: SE шлем прошёл безопасные +1/+2,

Вкладка «Личные» использует другой список: TWarehousesManager исключает
шаблон30 в CheckItemForFilters (9159EE..9159F9) и ResortOutputList
(9171A9..9171B4). При диагностике четыре набора 1005/1066/1067/1068 оставались

Адаптер `tools/upgrade_kit_warehouse.js` заменяет только два `xor ebx,ebx`
(9159F7,9171B2, байты33DB) на NOP в памяти процесса. Оба адреса проверяются
до записи. Сохраняются предыдущие и следующие проверки поиска, категории,
принадлежности и других типов предметов. Глобальный предикат
IsSimpleUpgradeKit не меняется. Лаунчер подключает адаптер при каждом запуске.

24 комбинации исходных фильтров выполнены в Unicorn: до/после исправления,
шаблоны30/19/301, предыдущее решение фильтра0/1. Ранее отклонённые предметы
не становятся разрешёнными. Ещё20 существующих тестов склада пройдены.
На временной базе проверен полный путь: набор→склад6A→инвентарь30→успешное
улучшение C8/2A. ID и запись набора при переносе сохранены. Основной аккаунт
этими тестами не изменялся. Отчёты: upgrade_kit_inventory_native.json,
upgrade_kit_warehouse_roundtrip.json, upgrade_kit_warehouse_live.json.

Исправление применено к текущей игре без перезапуска. Для пересборки списка
нажать зелёную кнопку обновления справа внизу вкладки «Личные».
Визуальный результат и перенос мышью ещё проверяет пользователь.
