# Третий этап: восстановление незавершённых боёв

Поставка завершена 1 октября 2026 года. Основной `tio-server` на `185.184.42.88` обновлён в 17:54:24 UTC; аварии проверялись только на отдельных тестовых процессах.

## Сохранение действия и восстановление

Основной многопользовательский сервер сохраняет общий снимок матча в `battle_checkpoints`, а исключительные привязки аккаунтов — в `battle_checkpoint_members`. Изменения сохранённых вещей, навыков, оплаты входа и итоговых наград присоединяются к той же SQLite-транзакции, что и снимок. Ответы об успешном действии передаются после коммита. Ошибка сохранения откатывает изменения БД, поля и очередей ответов. Остальные операции хранилищ используют прежние самостоятельные транзакции.

Снимок содержит карту, глобальные и локальные ID бойцов, HP/AP, команды, инвентарь, навыки, эффекты, видимость, двери, добычу, историю урона и убийств, боевой опыт, достижения, состояние генераторов случайных чисел и оставшееся время. Для шахты сохраняются залежи, временные предметы и NPC; для тира — оплаченный вход, мишени и исходный срок сеанса.

При запуске сервер восстанавливает снимки до открытия входа. Оба аккаунта подключаются к одному прежнему полю через существующий протокол загрузки сцены. Сохранённое действие не воспроизводится повторно. Таймеры учитывают прошедшее реальное время и новый monotonic clock; рестарт не выдаёт полный новый ход. Работает прежнее окно переподключения 180 секунд. Если оно истекло, применяется существующее правило выхода, с однократным расчётом. Штатная остановка по-прежнему завершает бои; продолжение предназначено для неожиданной потери процесса.

Сохранённый окончательный отчёт и уже применённая квитанция награды имеют приоритет над более старым активным полем, например после прерывания штатной остановки. Такой бой заканчивается через существующую очередь расчёта и не продолжает принимать игровые действия. Повтор не меняет уже начисленные деньги, статистику и XP. После ухода участников снимок и привязки удаляются.

Снимок — JSON версии 1 с фиксированным списком разрешённых классов, контрольной суммой и отпечатком правил. `pickle`, произвольные импорты, сокеты и пароль сессии в снимке отсутствуют. Неизвестная версия, несовместимые правила или повреждённый снимок останавливают только затронутый матч и блокируют вход его аккаунтов до разбора; здоровые матчи восстанавливаются независимо. Ошибка общего хранилища остаётся причиной остановки сервиса. Для будущего изменения правил требуется совместимая миграция снимка либо предварительное завершение матчей.

Эти правила восстановления — инженерное поведение эмулятора. Они не объявляются историческими алгоритмами закрытого сервера TIO. Снимки покрывают уже реализованные режимы; общий цикл налётчика/защитника шахты по-прежнему не реализован.

## Внешняя резервная копия

По выбору пользователя копия хранится в `%LOCALAPPDATA%\TIO-emulator\backups` на этом Windows-компьютере. `tools/offsite_backup_windows.py` получает через SSH согласованный SQLite-снимок, действующий код, каталоги, обязательные XML/JSON runtime-ресурсы, список зависимостей, конфигурацию и systemd unit. Удалённый временный каталог имеет закрытые права и удаляется после передачи. Локально открытая БД/архив на диск не записываются: данные шифруются Windows DPAPI для текущего пользователя. Каталог ограничен ACL этого пользователя.

Проверка расшифровывает архив в память, проверяет SHA256 БД, наличие кода/config и восстанавливает SQLite в памяти для `PRAGMA integrity_check`. Первая копия до поставки проверена с 91 аккаунтом: `tio-20261001T175343504532Z.dpapi`.

Создать новую копию:

```powershell
python tools/offsite_backup_windows.py
```

Проверить имеющуюся:

```powershell
python tools/offsite_backup_windows.py --verify "$env:LOCALAPPDATA\TIO-emulator\backups\tio-20261001T175343504532Z.dpapi"
```

Для ручного восстановления можно явно расшифровать проверенный архив в **новый** каталог (открытая копия появится только по этой команде):

```powershell
python tools/offsite_backup_windows.py --verify "$env:LOCALAPPDATA\TIO-emulator\backups\tio-20261001T175343504532Z.dpapi" --export-new "$env:LOCALAPPDATA\TIO-emulator\backups\recovery-20261001"
```

Далее устанавливаются Python/зависимости и код на новом сервере; БД переносится только при остановленной службе с проверкой владельца `tio` и прав. Существующую БД сначала сохраняют отдельно. Конфигурация и unit требуют проверки путей и адреса нового VPS. Нельзя применять команды первичной установки к живой БД поверх сохранений.

DPAPI зависит от профиля Windows и его ключей. Архив сам по себе не переносимый ключ восстановления: для переезда нужен сохранённый профиль/ключи либо расшифровка на этом компьютере. Потеря VPS покрывается внешней копией, одновременная потеря VPS и этого профиля — нет. Автоматическая внешняя отправка и её расписание не установлены.

Действующий ежедневный VPS-таймер проверен: `tio-backup.timer` enabled/active, копия 1 октября в 03:05:06 UTC завершилась успешно. Существующая политика 14 дней сохранена. На VPS продолжают работать ежедневные копии; они сами по себе не покрывают потерю всего VPS. Согласованный live-снимок использует [официальный SQLite Backup API](https://www.sqlite.org/backup.html); сохранение состояния и экономических изменений в одном коммите следует модели [атомарного коммита SQLite](https://www.sqlite.org/atomiccommit.html).

## Проверки и эксплуатационные пределы

Доказательства находятся в `reports/stage3-battle-recovery`. `tests/test_battle_crash_recovery.py` проверяет медицинское действие, откат после ошибки записи снимка, абсолютные таймеры, RNG, восстановление двух аккаунтов, повреждённый матч среди независимых, завершение без повторных наград, оплату тира и состояние шахты. Два отдельных процесса завершаются через `os._exit` до/после коммита. Ещё один тест принудительно завершает отдельный TCP-сервер и подключает к перезапущенному серверу оба аккаунта через настоящий native wire protocol.

Нагрузочный сценарий — четыре одновременных авторитетных матча, восемь независимых сохранённых инвентарей и 160 корректных окончаний хода. Измеряется время обработчика и коммита на временной SQLite, без клиентской графики и публичной сети. Это ограниченная проверка текущей ёмкости, а не доказательство поддержки произвольного числа игроков. Сохранение полного JSON-снимка увеличивает стоимость действий; для дальнейшего масштабирования нужно измерять реальные профили нагрузки, сокращать повторную сериализацию неизменяемых правил и учитывать общий серверный lock.

Подготовка поставки: `tools/prepare_battle_recovery_deploy.py`; guarded обновление: `tools/deploy_battle_recovery_remote.py`; изолированная проверка кандидата/поставленного кода: `tools/verify_battle_recovery_remote.py`; основной публичный сервис: `tools/verify_hosted_battle_recovery.py`; сохранность прежних строк и хэши: `tools/inspect_battle_recovery_hosting.py`.

Обновление переносит только 47 исходных файлов. Перед остановкой проверяются живые подключения; до замены сохраняются согласованная удалённая БД, прежний код/config и unit. При ошибке откатывается код, без восстановления устаревшей БД поверх данных игроков. В ходе основной публичной проверки создаются два новых QA-аккаунта, сохраняемые для аудита. Принудительная авария основного сервиса не выполняется. Проверка несколькими оригинальными графическими клиентами остаётся отдельной задачей.
