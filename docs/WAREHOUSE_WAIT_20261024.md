# Перенос брони после нескольких попыток — 24.10.2026

## Сообщение игрока и границы диагностики

Игрок сообщил около 14:07 по Хельсинки, что броня переносится в личный склад
примерно с десятой попытки; симптом встречался у шахты и в Reservation.
Проверен журнал с 14:00 (11:00 UTC). В 14:07:12–14:07:16 есть переход
соответствующего игрока из города к входу в шахту. Сервис работал без перезапуска.
Обычный журнал не сохраняет пакеты или причины складских отказов, поэтому
конкретную последовательность запросов игрока восстановить нельзя.

Причина именно этого эпизода **не установлена**. Ниже описан отдельно
воспроизведённый дефект, способный вызвать такой же симптом. Двухсекундный
пассивный опрос склада не задерживает ответы на принятые операции переноса.

## Подтверждённый дефект

`tio/city_inventory.py:city_inventory_replies` молча отбрасывал непустой
запрос `2F`, если ни один запрошенный ID бойца уже не существовал в отряде.
Такое поведение изначально предотвращало фиктивные инвентари и ошибки магазина
при открытии городских меню, но не учитывало контракт ожидания клиента.

Оригинальный неизменённый `silver.dll` проверен в Unicorn:

1. Построитель `98ffc4` отправляет `2F` и устанавливает общий флаг ожидания
   через `990050 -> 9dc760`.
2. Указатель `ac5940` действительно ссылается на `ac4c58`, тот же флаг.
3. Построитель переноса `992294` при установленном флаге выходит через
   `9922d2 -> 992407` до получения транспорта. Десять повторных попыток
   не отправляют ни одного `6B`; сервер не может обработать эти переносы.
4. Ответ `30` с настоящим, известным клиенту основным бойцом проходит
   потребитель `990638` и снимает ожидание через `990b93 -> 9dc760`.
   Следующая попытка сразу отправляет правильный `6B`.

На установленном серверном исходнике отдельно проверен чистый вызов с
синтетическими данными: устаревший ID22 при существующем основном ID1
возвращает ноль ответов. Производственная БД для этой проверки не открывалась.

## Исправление

Для непустого запроса, не давшего ни одного действительного инвентаря,
`city_inventory_replies` возвращает настоящий текущий инвентарь основного
бойца ID1 через уже существующий поиск, ограниченный аккаунтом сессии.
Это обычный авторитетный снимок `30`, который завершает ожидание клиента.

Инвентарь отсутствующего бойца не создаётся. Если действительный ответ уже
есть, лишний основной снимок не добавляется. Пустой запрос остаётся без ответа.
Если основной боец отсутствует, фиктивный ответ также не создаётся; игровая
городская сессия предполагает существующего основного бойца.

Никакие предметы, деньги, схемы БД, правила экипировки или операции переноса
этим исправлением не меняются. Не добавляется автоматическая повторная
отправка изменяющих состояние запросов.

## Проверки

- TDD: до исправления упали три новых проверки: одиночный устаревший ID,
  повторные устаревшие ID и получение ответа по настоящему TCP.
- `tests/test_city_inventory_wait.py`: четыре проверки чистой функции и два
  сценария с двумя авторизованными TCP-клиентами. У аккаунтов разные экземпляры
  брони. Проверены изоляция, завершение устаревшего чтения, перенос и возврат
  Female Exo Armor с первой команды у шахты13 и в Reservation3, сохранение
  экземпляра и прочих метаданных.
- `tests/test_city_inventory.py`: сохранены проверки пустого запроса,
  повторов и смешанного списка существующих/устаревших ID; ожидание для
  отсутствующего бойца исправлено в соответствии с протоколом.
- `tools/verify_warehouse_wait_native.py`: оригинальные построители,
  декодер и потребитель; десять заблокированных переносов, снятие ожидания
  и следующий успешный `6B`. GUI, управляемые строки и поиск синтетического
  актора изолированы явно. Клиентская DLL не менялась.
- Новые стандартные тесты добавлены в переносимый `tools/run_server_checks.py`.

Полные результаты локального baseline, CI и изолированной проверки на VPS
указываются в PR. Нативная эмуляция и TCP-клиенты не заменяют повторение
эпизода в графическом клиенте игрока.
