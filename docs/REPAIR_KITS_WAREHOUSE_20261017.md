# Невидимые ремкомплекты на складе — подготовленное исправление

Статус: **опубликовано по указанию пользователя, версия2026.10.17.1**.
Код сервера и сохранения игроков не менялись. Перезапуска службы не было.
Работающую игру нужно закрыть, затем получить обновление через лаунчер.

## Причина

В актуальной опубликованной версии клиента `2026.10.15.2` менеджер склада
безусловно исключает шаблоны17,18,19 из отображаемого списка. Нативная функция
`a7b8c0` определяет ремкомплект по диапазону `17 <= template_id <= 19`.
После её вызова две ветви обнуляют результат фильтрации:

| Ветвь | Исключение | Исправление |
|---|---|---|
| Проверка предмета для фильтров | `9159c7: xor ebx,ebx` | два `nop` |
| Пересборка списка | `917177: xor ebx,ebx` | два `nop` |

Из-за этого сервер продолжает считать сохранённый предмет занятым местом,
но клиент убирает его из списка. В прочитанных строках хостинга присутствуют
ремкомплекты всех трёх типов с корректными ID, количеством, ресурсом и
снятым состоянием экипировки. Это подтверждает сохранность этих строк,
а не удаление предметов при переносе. Проверка выполнена без выгрузки базы,
логинов, паролей или изменения аккаунтов.

## Что сервер ожидает от клиента

Обычный запрос переноса `6B`:

1. Вид склада `u8` — личный склад0.
2. ID своего бойца `u32`.
3. Количество записей для **помещения на склад** `u16`, затем пары
   `instance_id:u32, quantity:u32`.
4. Количество записей для **возврата бойцу** `u16`, затем такие же пары.

Клиент передаёт ID экземпляра и количество. Шаблон и ресурс ремкомплекта
сервер берёт из сохранённого предмета в принадлежащем аккаунту источнике.
Для ремкомплекта отдельный запрос или особый формат переноса не нужен.
Запрос чтения личного склада — `69 00`.

После принятого переноса сервер возвращает инвентарь бойца `30` и список
склада `6A`. В записи `6A` присутствуют ID экземпляра, шаблон, количество,
текущий/максимальный/расчётный ресурс и метаданные. Эти поля уже передаются
для ремкомплектов. При частичном использовании набор остаётся отдельным
экземпляром с тем же остатком ресурса. Нумерация сегментов начинается с0.

Склад привязан к городу. Исправление не раскрывает предметы другого города
или аккаунта и не меняет вместимость. Поиск, категории и ограничения прав
остаются действующими: удаляется только безусловное скрытие ремкомплектов.

## Готовый кандидат

Трансформер: `deploy/client_repair_warehouse.py`.

Исходный опубликованный `silver.dll`, 8163840 байт:

`8b163bea1a13ec994d379094ab6c59034955e99fc7c2d6f98c605fc583e30e4b`

Кандидат того же размера:

`9a8fb8f12af25c6c81a96ac623b1217b4deaeaa1008d5c4e3ead8feba9ff75ed`

Изменены **ровно четыре байта**. Трансформер проверяет SHA256 всего исходного
релиза и границы обеих инструкций. Сетевой протокол, идентификаторы предметов,
прочие фильтры, ресурсы и серверные файлы не меняются. Установленный на этом
компьютере клиент также не заменялся.

Уже сохранённые ремкомплекты не требуют пересоздания или компенсационного
начисления. После будущей установки клиент сможет включать их в обычный
список доступных предметов склада при подходящих городе и фильтрах.

## Результаты проверки

- **864 нативных сценария:** фактический опубликованный DLL и кандидат,
  обе ветви списка, два адреса загрузки DLL, три вида склада, шаблоны
  внутри и за пределами диапазона ремкомплектов, принятые/отклонённые
  предыдущие и последующие фильтры. Выполняется настоящая функция
  распознавания ремкомплектов. Старый клиент воспроизводит скрытие;
  кандидат сохраняет результат остальных фильтров.
- **9 нативных проверок протокола:** направление двух массивов запроса,
  помещение и возврат всех трёх видов, список с полным и частично
  использованным ресурсом. Код проверенных нативных функций совпадает
  с текущим опубликованным клиентом.
- **23 серверные проверки** на изолированной копии фактического кода
  хостинга и временной локальной SQLite: покупка всех трёх видов,
  `6B→30/6A`, повторное чтение, возврат с сохранением ID и ресурса,
  повторное помещение без дублирования, одновременная работа двух
  аккаунтов, разделение городов, вместимость и откат неудачных операций.

Это нативное выполнение с синтетической памятью и автоматическая проверка
протокола/сохранений. Графический клиент с кандидатом не запускался;
визуальная приёмка и проверка после публикации ещё не выполнялись.

Широкий предварительный прогон неизменённого сервера сохранён отдельно:
в нём есть старые ожидания золотой оплаты SC/аренды, количества предложений
и порядка ответа при отсутствии доступа к клановому складу. Они не относятся
к этому исправлению; успешные23 проверки не выдаются за весь тестовый набор.
