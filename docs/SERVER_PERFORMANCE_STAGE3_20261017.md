# Повторные чтения состава, групп и положения — 17.10.2026

## Поведение

`OwnedPetStore.list` по-прежнему выполняет синхронизацию уровней и рангов в
одной транзакции записи. Полученные pet/inventory строки передаются в
`project_saved_roster`: правила владения оружием загружаются один раз, каталог
пассивных умений — лениво один раз, наличие ability_states проверяется один раз.
Повторные SELECT inventory_packet для каждого бойца устранены. Профили умений
читаются по account/pet_id. Проверки владельца и целостности пакетов сохранены.
Данные и правила не сохраняются между запросами; изменения конфигурации видны
при следующем чтении состава.

`PartyStore._snapshot` читает участников и их выбор одним LEFT JOIN вместо
отдельного запроса выбора каждого участника. Сохраняются порядок участников,
порядок выбранных бойцов и участники с пустым выбором. `info`, `route`, `current`,
`travelling` и разрешение дополнительного персонажа принимают существующее
соединение. Это позволяет согласованно читать группу и координаты в одном
SQLite read snapshot без дополнительных соединений.

`PartyLocations` строит представление только на время одного вызова. В refresh
группа, маршрут и координаты читаются один раз. Пока маршрут не завершён,
транзакция записи не открывается. Наступление срока — только предварительная
проверка: `arrive` повторно проверяет маршрут и участников в writer transaction,
после чего ответ строится по свежему снимку. Переезд, лидерство, принадлежность
персонажа и согласие участников не берутся из долгоживущего кэша.

## Изменённые файлы этого этапа

* `tio/owned_pets.py`, `tio/passive_stats.py` — проекция состава.
* `tio/travel_party.py` — состав группы и использование соединения вызывающего кода.
* `tio/party_travel.py`, `tio/locations.py` — согласованное чтение положения и маршрута.
* `tio/character_identity.py` — проверка дополнительного персонажа в том же снимке.

Пакет установки дополнительно содержит три ранее подготовленных файла этапа 2:
списки комнат и быстрый обход графа checkpoint. Они не были установлены ранее
из-за активного боя. Объединение позволяет выполнить один перезапуск.

## Измерения

Временные SQLite с четырьмя аккаунтами; состав из четырёх бойцов; группа из четырёх
участников. Данные совпадают по хешам во всех четырёх сценариях до/после.
Это отдельные тестовые базы, реальные hosted-аккаунты в benchmark не участвуют.

| Операция | SELECT до → после | BEGIN IMMEDIATE до → после | Медиана на VPS до → после |
|---|---:|---:|---:|
| Прочитать 4 бойцов | 18 → 11 | 1 → 1 | 11,57 → 8,60 мс |
| Обновить положение 4 участников в городе | 196 → 44 | 4 → 0 | 21,40 → 3,82 мс |
| Узнать город 4 участников | 48 → 32 | 0 → 0 | 5,99 → 3,44 мс |
| Обновить положение 4 участников в пути | 188 → 32 | 4 → 0 | 18,26 → 3,22 мс |

По 30 измерений на вариант, после прогрева. Это последовательное сравнение
изолированных fixture под текущей нагрузкой VPS, а не строгий A/B всей игры.
Число SQL и совпадение результатов — более устойчивые показатели, чем абсолютные
миллисекунды. Локальные результаты также сохранены в отчётах.

Нулевое число writer begin относится именно к `PartyLocations.refresh` до срока
прибытия. Другие пути (`ContractsService.sync`, `set_online`, `recover_leader`,
`ContractStore.target_for`) ещё содержат самостоятельные транзакции. Они не
изменяются этим пакетом; следующий кандидат — отдельная проверка отрицательных
веток этих операций с повторной валидацией под writer lock при необходимости.

## Проверки

Добавлены девять проверок: эквивалентность одиночной/пакетной проекции,
свежесть здоровья/умений при совпадающих ID разных аккаунтов, откат при
некорректном профиле, старые базы без таблицы умений, порядок и пустой выбор
в группе, отсутствие пустой записи при простое и движении, повторная проверка
изменившегося маршрута, принадлежность дополнительного персонажа в переданном
соединении. Проверки также охватывают существующие маршруты/контракты, прибытие,
rollback, ранги, вес, снаряжение, лечение и переключение персонажей.

В исходном hosted-коде обнаружены два несовместимых старых теста этого набора:
`test_all_item_weights_match_imported_original_source` не учитывает уже
существующие предметы 5001–5012; `test_native_creation_secondary_selection_purchase_restart_primary_preserved`
периодически получает баланс 3000 вместо ожидаемых 2700 (на исходном и новом коде).
Они исключаются только по точным именам; исходные результаты сохранены.
После исключения этих двух старых несовместимостей прошли 143 целевых теста
локально и в изолированной копии на VPS. Дополнительно прошли 122 проверки
совместимости пакета локально и на VPS; в этом ранее существовавшем наборе
отдельно учтены 16 известных старых сбоев из отчёта этапа 1. Весь репозиторий
не объявляется зелёным. Полные списки исключений и результаты сохранены в JSON.
Дополнительный файл provenance отсутствовал в hosted-дереве и предоставлен
только изолированным тестовым копиям. На рабочий сервер он не устанавливается.

До установки проверены два настоящих TLS-подключения: общая комната, адресация
ID, создание частной travel-party, приглашение/принятие, готовность обоих,
общий переход в текущий город, статус и роспуск. Инвентари не изменились.
QA использует зарезервированные имена, исключённые из рейтингов; фикстуры
удалены, осталось 19 аккаунтов, integrity_check=ok. Проверка движения группы
между разными точками здесь выполняется автоматическими fixture; hosted-прогон
проверяет прибытие в тот же город. Графический клиент не проверялся.
