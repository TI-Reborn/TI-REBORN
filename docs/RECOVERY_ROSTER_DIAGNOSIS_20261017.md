# Лечение нескольких бойцов и обновления экипировки

Проверка выполнена по прямому запросу для аккаунта `player_two`.
Доступ к аккаунту ограничивался чтением SQLite в режиме `mode=ro`;
вход вместо игрока, лечение, переодевание, списание денег и изменение
его сохранений не выполнялись.

## Наблюдение

Во время проверки одновременно пассивно восстанавливались бойцы2 и4.
В двух согласованных снимках их HP выросли с26 до35. У остальных двух
бойцов HP не изменились. Содержимое и флаги экипировки всех четырёх
инвентарей совпали побайтно. Во всех полях анкет, кроме HP лечившихся
бойцов, изменений не обнаружено. ID анкет и владельцев инвентарей правильные.

Таким образом, во время наблюдения смешивания характеристик или перемещения
экипировки **в сохранениях** не обнаружено. Это не исключает визуальный сбой.

## Подозрительный механизм

`RecoveryStore.refresh` отправляет полный `PetInfo66` при каждом приросте HP.
Городской обработчик платного лечения также пересылает анкеты всего отряда.

Выполнение оригинального нативного обработчика с прочитанными анкетами
бойцов2 и4 подтвердило: `66` повторно вызывает применение слотов экипировки
(`98f978`, одиннадцать слотов человека либо три слота питомца), пересчёт
модели и уведомление списка наёмников (`8731cc`). Это происходит и для
невыбранного бойца. Полная анкета не является нейтральным обновлением HP.

Графические callbacks в нативной проверке изолированы. Она подтверждает
лишние операции, но **не доказывает конкретную видимую перестановку**
характеристик или одежды. Проверенный числовой UI-кэш при этих анкетах
сам по себе не перезаписался; обратное не заявляется.

Также найден пробел в блокировке пассивного восстановления: старая
проверка видела только частную арену сессии, хотя общие бои живут
в `router.team_arena`. Городские сообщения с локальными ID бойцов
не должны попадать в активную общую сцену.

## Подготовленное изменение

Статус: **локальный кандидат, на хостинг не установлен**.

- При обычном приросте здоровья отправляется `4E`, атрибут4, с ID
  конкретного бойца и абсолютным HP. Его характеристики и экипировка
  повторно не загружаются. При настоящем изменении ранга полный профиль
  сохраняется — такие обновления не отбрасываются.
- Городской обработчик платного лечения возвращает кошелёк и HP только
  запрошенных бойцов. Оплата, лечение и подготовка ответов объединены
  одной транзакцией. Повторное лечение уже здоровых бойцов не списывает деньги.
- Пассивное восстановление приостанавливается и для общей арены.

Изменены ровно два файла кандидата:

`tio/battle_recovery.py`, `tools/loopback_exchange.py`.

Адаптер взят из реального кода хостинга. Локальная рабочая версия этого
файла отличается от хостинга и не должна выгружаться целиком; готовый
архив содержит проверенную версию из `work/recovery-roster-20261017/candidate`.
Общий обработчик лечения на экране результатов `TeamArena.treatment`
в этот кандидат не включён. Визуальный эффект этого отдельного пути
не проверен и его изменение не заявляется.

## Проверка

Прошли68 автоматических проверок на изолированной копии фактического
серверного кода: одновременное восстановление нескольких бойцов, разные
аккаунты, повторная обработка одного тика, расход денег и откат платного
лечения, неизменность инвентарей и всех полей кроме HP, способности,
экипировочные бонусы, ранги и восстановление боёв.

Проверка с настоящим `TeamArena` подтверждает блокировку городского
восстановления у двух участников общего боя при пустых частных аренах
и доступность восстановления для третьего аккаунта вне боя.

Нативная проверка `4E/status4` подтверждает изменение только текущего HP
адресованной модели до первого UI-callback: другие поля этой модели,
экипировка и другая модель остаются нетронутыми.

Это не визуальная приёмка и не проверка развёрнутого серверного исправления.
Во время подготовки на хостинге были три подключения и один сохранённый
активный бой; службу для этого кандидата не перезапускали.
