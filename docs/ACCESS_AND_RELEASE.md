# Доступ и выпуск

## Бесплатная схема работы

Целевая организация: **TI-Reborn**, тариф GitHub Free. Репозиторий **TI-Reborn/TI-REBORN** остаётся **Private**.
Описанная ниже схема применяется после переноса и проверки доступа; этот документ сам
по себе не подтверждает, что перенос или приглашение уже выполнены.
Владелец Junduge сохраняет административный доступ. Разработчик ilyaplot получает
роль **Read** только для этого репозитория как внешний участник (outside collaborator).
Не выдавайте ему Write, Maintain, Admin, роль владельца организации или доступ через
команду с более широкими правами.

Разработчик создаёт приватный fork в своём личном аккаунте, работает в его ветках
и открывает pull request в основной репозиторий. В исходном репозитории у него нет
права push или merge. Владелец проверяет изменения и сам выполняет merge.

На бесплатном тарифе закрытого репозитория обязательный review через branch protection
не применяется. Контроль здесь обеспечивается отсутствием у разработчика права записи.
CODEOWNERS описывает ожидаемого рецензента, но не считается механизмом защиты.

## Настройки владельца

- Организация: тариф Free, владельцем остаётся Junduge.
- Base permissions: None; доступ к каждому репозиторию выдаётся отдельно.
- ilyaplot: outside collaborator, роль Read только для TI-REBORN.
- Разрешить private forks в настройках организации и конкретного репозитория.
- Fork создаётся в личном аккаунте разработчика: GitHub Free не позволяет размещать
  приватный fork в другой бесплатной организации.
- Основной репозиторий и fork остаются закрытыми.
- Production-ключи и данные игроков не добавлять в GitHub Actions или репозиторий.
- CI из pull request не должен получать production-доступ.

Человек с чтением может скачать весь код. Разрешения не ограничивают чтение отдельных
папок внутри одного репозитория. Отзыв доступа не удаляет уже скачанную локальную копию.

## Работа разработчика

1. Принять приглашение Read.
2. На странице основного репозитория нажать Fork и выбрать личный аккаунт.
3. Клонировать свой fork, создать ветку задачи, внести изменения и выполнить тесты.
4. Открыть pull request из своего fork в main основного репозитория.
5. Владелец проверяет diff и результаты CI, затем принимает или отклоняет PR.
6. Выпуск на хостинг выполняется отдельно владельцем.

## Выпуск

Перед игровым выпуском владелец проверяет фактическое состояние хостинга, сохраняет
согласованную резервную копию базы и предыдущие код/конфигурацию. Локальная база никогда
не заменяет hosted-базу. После обновления: preflight, состояние службы, журналы, проверка
несколькими аккаунтами и отдельно настоящими игровыми клиентами, очистка своих QA-фикстур.
Старые команды в DEPLOY_HETZNER.md и deploy/BACKUPS.md необходимо сверять с текущим
удалённым состоянием. Подготовка GitHub не меняет production и не подтверждает совпадение
локального снимка с работающим сервером.
